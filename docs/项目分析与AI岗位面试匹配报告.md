## 一、一句话定位（非常重要，先想清楚）

**这不是一个 Agent 项目，而是一个"生产完成度很高的 RAG + 文档智能应用"，附带了弱工具调用能力。**

面试时如果把定位说错（自称做了个 Agent 系统），会被面试官在 ReAct / 规划 / 工具自主选择几个问题上连环问穿。
**正确的自我定位**：以 RAG 为核心的知识库问答系统，在检索链路深度、工程化落地、评测体系三块做到了生产级，Agent 能力处于"单点工具调用"的早期阶段，并有清晰的演进路线。

这个定位反而是优势——市面上自称 Agent 的简历项目 90% 是 Demo，而本项目是真的能部署上线的。

## 三、真实技术资产（简历上能写、能被追问到底的）

### 3.1 检索链路 —— 这是全项目最硬的部分

1. **混合召回**：FAISS 稠密召回 + 自研 BM25 稀疏召回
   - 自研 BM25 中文分词策略：中文单字 + 相邻二元片段，英文/数字整词，**不引入 jieba 等额外依赖**
   - 这是一个有意识的成本权衡，面试时可以展开讲为什么
2. **RRF 融合**：`rrf_score = Σ 1/(k0 + rank)`，两路候选去重叠加
3. **Rerank**：本地 CrossEncoder（bge-reranker-v2-m3）或阿里云 DashScope qwen3-rerank，可在线切换；失败自动降级为原始相似度排序
4. **知识库路由**：可见库 ≤3 个直接全量检索；>3 个时先 broad search（top_k×10）按 kb_id 聚合相关度，选 Top-3 库再走混合召回
   - 这是**原创性设计**，面试中值得单独讲
5. **相关度过滤**：重排后低于 40% 的片段不进上下文
6. **意图改写**：LLM 查询重写，15s 超时保护

### 3.2 轻量 Self-RAG —— 有思考但只做了一半

- **证据充分性判断**：LLM 判断检索证据是否够回答问题，不足时返回"缺失要点"
- **单次改写重检**：用缺失要点引导改写查询 → 重检索 → 与首轮结果按 doc_id 去重合并 → 整体重排
- **引用编号核对**：正则扫描回答中的 `[来源 X]`，越界引用自动追加提醒，防模型编造引用
- 全程 15s 超时 + 异常降级为"充分"，不阻断主流程

### 3.3 llm-wiki 知识编译层 —— 独立技术思考的证明

借鉴 llm-wiki 思想（LLM 作为"知识编译器"），把原始碎片先编译成结构化百科词条再检索：
- **source 卡片**：入库后异步 LLM 提炼为"概述/关键要点/相关概念/原文精选"，写入向量库
- **digest 综合词条**：跨素材深度综合，带 `[来源 X]` 引用
- **检索优先命中**：百科卡片稳定排序前置，原始碎片兜底
- **失败静默降级**：异步、可关闭，不影响主链路
- Markdown 镜像落盘，可导出静态知识站点

这一块说明你**不是照抄开源 Demo，而是读了论文/项目思想后做了本地化翻译**（把 Claude Agent SDK 实现翻译为 FastAPI + 自有 Provider 体系）。

### 3.4 权限设计 —— 安全上有真思考

- **向量库物理隔离**：`_scoped_store` 按可见性重建 FAISS 子索引，检索从一开始就不触及无权限数据（不是"检索后过滤"）
- 公共库 / 个人库两级，私人库仅属主可见
- 游客身份禁止通过聊天框写入知识库，自动降级为仅识别

### 3.5 记忆与上下文管理

- **跨会话记忆**：LLM 抽取长期偏好/事实 → `user_memories` 表 → 按关键词重叠 + 重要度检索注入
- **敏感信息拦截**：正则过滤密码/token/身份证/银行卡，不落库
- **会话摘要压缩**：>20 条消息或 >12000 字符触发 LLM 压缩，失败降级为按条截断
- 抽取与摘要均为对话结束后的**后台异步任务**，不拖慢当前回答

### 3.6 回归评测 —— 2026 年最被看重、但多数候选人不具备的能力

- 评测集 + 用例管理（手工新增 / JSON 批量导入 / **从用户点踩反馈一键导入**）
- 三个指标：**检索命中率**（期望关键词/来源命中）、**引用忠实度**（LLM 判断答案是否被检索上下文支撑）、**LLM-as-Judge 1-5 分**
- 支持跨 run 对比，判断 prompt/检索/重排改动是否引入回退
- 点踩反馈自动转坏例 → 真实用户问题进回归集，这个闭环设计很有说服力

### 3.7 工程化 —— 区分 Demo 选手和工程选手的关键

| 手段 | 实现 |
|---|---|
| 事件循环解阻塞 | OCR 推理、Rerank 打分、向量化、批量上传统一 `asyncio.to_thread` |
| 并行流水线 | 知识检索与联网搜索并行执行 |
| 连接池复用 | LLM/OCR/Search/Rerank/Embedding 按配置缓存 httpx 实例 |
| 流式 | SSE 全链路阶段事件（rewriting/retrieving/reranking/gap_checking/generating） |
| 缓存 | metadata.json 按 mtime 内存缓存；Redis 文件缓存 + 60s 冷却降级 |
| 部署 | Docker Compose、镜像瘦身 75%、阿里云一键部署、定时备份、HTTPS |

## 四、对标 2026 主流 Agent 技术的差距

业界公认的八大 Agent 架构，逐项对照：

| 架构 | 主流做法 | 本项目现状 | 判定 |
|---|---|---|---|
| **RAG Agent** | 向量召回 + 重排 + 上下文注入 | 混合召回 + RRF + Rerank + 路由 + wiki 前置 | ✅ **强项** |
| **Memory-Augmented** | 四层分层记忆 | 会话摘要 + 跨会话长期记忆 + 知识库 | 🟡 有雏形，缺分层与冲突消解 |
| **Tool-Augmented** | LLM 自主选择工具 + MCP 协议 | **关键词硬匹配路由**（`_UPLOAD_KEYWORDS` 等） | 🔴 **代际差** |
| **Reflexive 反思** | 多轮自我校验迭代 | 仅单次重检 + 引用核对 | 🟡 半成品 |
| **ReAct 推理-行动循环** | Thought → Action → Observation 循环 | 固定线性流水线，无循环 | 🔴 缺失 |
| **Plan-and-Execute** | 任务分解 + 依赖编排 + 失败回滚 | 无 | 🔴 缺失 |
| **Multi-Agent** | Orchestrator + 专精子 Agent | 无 | 🔴 缺失 |
| **Autonomous Loop** | 目标驱动自治循环 + 终止条件 | 无 | 🔴 缺失 |

### 其他工程侧短板

1. **无 MCP / A2A 协议** — 2026 面试高频词，工具互通的事实标准
2. **无可观测体系** — 只有日志 + `tool_calls` 表，缺 Langfuse/LangSmith 级全链路 trace、token 成本追踪
3. **测试与 CI 薄弱** — 27 个用例、无 CI，与"生产级"定位不匹配
4. **prompt 散落在代码里** — 无版本管理、无 A/B 能力
5. **单机架构瓶颈**
   - SQLite 写锁：多用户并发写入会竞争
   - FAISS 每次 `save_local` 全量落盘，规模增长后 IO 压力大
   - `_scoped_store` **每次检索都重建子索引**（逐条 `reconstruct`），O(N) 复杂度，万级 chunk 后必然成为瓶颈
6. **无并发/压测数据** — 讲不出 QPS、P99 延迟，工程深度会被打折
7. **评测指标不全** — 缺 Recall@K、MRR、NDCG 等检索标准指标；judge 未做人类标注校准

## 五、改进清单（面试主动讲 = 加分项）

按优先级排，每一条都对应一个"我知道现在的问题在哪、下一步做什么"的信号。

### P0 — Agent 化（决定能否面 Agent 岗）

1. **工具路由升级为 LLM Function Calling**
   - 现状：`if "上传" in query → image_upload`
   - 目标：为每个工具写 JSON Schema，交给模型自主选择与填参，保留关键词作为兜底与意图校验
   - 顺带解决：工具参数抽取、多工具组合调用、用户意图歧义
2. **接入 MCP 协议**，把 OCR / 入库 / 搜索 / wiki 编译暴露为标准 MCP Server
3. **流水线改造为 LangGraph 状态图**
   - 固定线性 → 带条件分支、循环、重试、终止条件的状态机
   - 具体：证据不足 → 回到检索节点；工具失败 → 重试/换工具/降级；超预算 → 强制终止
4. **Self-RAG 从单次改为有界多轮**：`max_iterations=3` + 终止条件 + 结果去重防死循环

### P1 — 可观测与评测（决定能否面中高级岗）

5. **接 Langfuse / Phoenix**：全链路 trace、每步耗时、token 成本、失败率看板
6. **评测扩充**：加 Recall@K / MRR / NDCG；加工具调用准确率（工具名 + 参数是否正确）；建多轮对话评测集
7. **LLM-as-Judge 校准**：抽 50 条做人类标注，算与 judge 的一致性；明示 verbosity bias / position bias 的应对
8. **补 CI + 提测试覆盖率到 60%**，检索链路做 Mock 化的单测

### P1 — 性能与规模

9. **`_scoped_store` 优化**：改用 FAISS 的 `IDSelectorBatch` 在搜索时过滤，或按 kb_id 分库，避免每次检索 O(N) 重建
10. **FAISS 索引升级**：IndexFlatL2 → IVF / HNSW；持久化改增量；规模上限评估后考虑 Milvus / pgvector
11. **SQLite → PostgreSQL**，解决并发写锁

### P2 — 记忆与知识深度

12. **记忆分层 + 冲突消解 + 遗忘曲线**（当前只有关键词重叠检索，记忆冲突与过期无法处理）
13. **引入知识图谱 / GraphRAG**：手写笔记里实体关系密集，适合做实体抽取 + 关系检索
14. **prompt 版本化 + A/B 实验**，与回归评测打通形成闭环

## 七、面试话术

### 7.1 60 秒自我介绍版

> 我做的是一个手写笔记知识库问答系统，把用户的手写笔记照片 OCR 成文字后构建向量知识库，支持多用户、权限隔离的知识问答。
>
> 技术上我最花力气的是**检索链路**：FAISS 稠密召回加自研 BM25 稀疏召回做 RRF 融合，再用 CrossEncoder 或 DashScope 重排，相关度低于 40% 的片段直接丢弃；知识库超过 3 个时会先做一次路由检索选出最相关的 3 个库。另外借鉴 llm-wiki 的思路做了一层知识编译，把原始碎片提前编译成百科词条，检索时优先命中。
>
> 工程上我比较在意**不让它变成 Demo**：全链路做了降级和超时保护，OCR 和向量化都丢到线程池避免阻塞事件循环，还建了一套回归评测——用 LLM-as-Judge 加上检索命中率和引用忠实度三个指标，每次改 prompt 或检索策略都能跑一遍看有没有回退，用户点踩的问题会自动变成评测用例。
>
> 这个项目的 Agent 能力目前还比较初级，工具是用关键词路由的，下一步我打算改成 Function Calling 加 MCP，流水线也想用 LangGraph 重构成带循环和终止条件的状态图。

最后一段主动交底 + 给出路线，是所有回答里最加分的一句。

### 7.2 必考题：你这个算 Agent 吗？

**不要硬撑，也不要自我否定。推荐答法：**

> 严格说不算。它现在是一个 RAG 流水线加单点的工具调用——工具的路由还是关键词匹配的，没有 ReAct 那样的 Thought-Action-Observation 循环，也没有任务规划。
>
> 我当时这么设计是有取舍的：这个场景的用户意图比较集中，关键词路由的准确率足够，而且可控、零额外 token 成本、不会误写知识库。但我清楚这是早期形态，真正的 Agent 化需要模型自主选工具，所以下一步是接 Function Calling 和 MCP，再用 LangGraph 把固定流水线换成状态图。

**面试官要的不是"我有 Agent"，而是"你知道 Agent 是什么、知道你现在在哪、知道怎么走过去"。**

## 八、高频追问预判与回答要点

| # | 追问 | 回答要点 / 当前弱点 |
|---|---|---|
| 1 | 为什么用 RRF 而不是加权求和？ | 两路分数尺度不同（余弦相似度 vs BM25 分值），RRF 只用排名不用分数，免归一化、对尺度不敏感 |
| 2 | BM25 为什么自己写？中文单字+二元切分的优劣？ | 权衡：省掉 jieba 依赖与部署体积；单字保证召回、二元补语义。**弱点**：未与 jieba 做对照实验，应承认并说会用评测集做消融 |
| 3 | chunk_size / overlap 怎么定的？ | **当前弱点**：配置化的，但无实验数据。诚实说，然后讲思路——用评测集的 Recall@K 做参数扫描 |
| 4 | 相关度阈值 40 怎么来的？ | **弱点**：经验值。应讲动态调整思路（按查询类型、按分数分布自适应） |
| 5 | Self-RAG 为什么只重检一次？ | 延迟与 token 成本权衡，单次已覆盖大部分缺口。**改进**：改为有界多轮 + 终止条件 |
| 6 | 权限为什么在向量层做？子索引重建复杂度？规模大了怎么办？ | **这是最有深度的一题**。O(N) reconstruct 在万级 chunk 会崩，正解是 `IDSelectorBatch` 搜索时过滤或按库分索引。答出这个非常加分 |
| 7 | 引用编号用正则核对，模型写 `[来源 3][来源 5]` 会漏吗？ | 正则用 finditer 全局匹配，能覆盖；**弱点**：无法验证"编号对但内容错"（引用了来源1却说的是来源2的内容），需更深的忠实度校验 |
| 8 | LLM-as-Judge 的偏差怎么校准？ | verbosity bias（偏爱长答案）、position bias；正解是抽人类标注样本算一致性，本项目**尚未做**，要主动承认 |
| 9 | 记忆冲突了怎么办？ | **当前弱点**：只有关键词检索，无冲突消解、无遗忘机制。改进方向：时间戳 + 重要度衰减 + 冲突时 LLM 仲裁合并 |
| 10 | 并发下 SQLite 写锁 + FAISS 全量保存怎么办？ | WAL 已开，但写入竞争仍在；正解是迁 PostgreSQL + FAISS 增量持久化/换 Milvus |
| 11 | SSE 断连怎么办？ | **当前弱点**：无重连与断点续传。正解：Last-Event-ID + 服务端事件缓存 |
| 12 | 压测数据？QPS、P99？ | **必须提前补测**，否则工程深度会被打折。至少本地用 locust 跑一组数据 |

## 九、总结

**这个项目的真实价值在"深度 + 完成度"，不在"Agent"。**

- 检索链路的深度（混合召回 + RRF + Rerank + 库路由 + wiki 前置）超过绝大多数同级别简历项目
- 回归评测体系是稀缺能力，2026 年这是面试官重点筛选的技能
- 工程化完成度是真的——能上线、有降级、有部署文档
- Agent 维度是明确短板，**主动交底 + 给出演进路线，远好于硬撑**

**优先级**：先补 P0（Function Calling + MCP + LangGraph 状态图），把 Agent 岗从"慎投"变成"可投"；同时补一组压测数据和 Recall@K 消融实验，把工程深度坐实。
