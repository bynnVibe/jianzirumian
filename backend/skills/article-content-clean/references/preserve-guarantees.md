# 保留契约与边界案例（L3 参考）

本文件是 `article-content-clean` 的执行层参考，仅在需要保留契约细则/边界判定时按需加载。
对应实现：`app/services/article_clean.py`；消费入口：`POST /api/knowledge/polish-ocr`。

## 1. 硬契约（不可违背）

| 契约 | 含义 | 实现保证 |
| --- | --- | --- |
| 只减不增 | 不新增任何字符/观点/句子 | 全程仅 `subn`（删角标）、`sub`（折叠空格）、`continue`（删行），无拼接新内容 |
| 保序 | 输出行顺序 = 输入行顺序 | 单次顺序遍历 `text.splitlines()`，`out_lines.append` 保序 |
| 子序列 | 输出行是输入行的子序列 | 每输出行都源自某输入行（删角标/折叠空格后），不重排不合并 |
| 保自然段 | 单个空行保留为段落分隔 | 空行仅在 `prev_blank` 时压缩，首个空行保留 |
| 保句完整 | 不切碎正文句 | 噪声只删**整行命中**；角标只删角标本身 |
| 可复现 | 同输入同策略同输出 | 纯函数、无随机、无外部状态 |
| 可审计 | 每类删除有计数 | `stats` 回传 removed_lines/removed_footnotes/collapsed_spaces/extra_patterns_removed/before_chars/after_chars |

> 借鉴 mr-obsidian「严格保留原文完整性」：即使后续做结构化（TOC/分节/摘要），也**不得丢失原文**；
> 本技能定位在结构化之前的「去噪」，只负责减，不负责重组或概括。

## 2. 边界案例

- **正文短句 vs 纯符号行**：`_SYMBOL_ONLY_RE` 命中且长度 ≤40 才删，避免误删 `好的。`、`——` 之类正文。
- **长文中提及「验证码」**：噪声规则不含此类词（那是抓取层 `RESTRICTED` 的职责），清洗层不会误删含「验证码」的正文句。
- **角标删空整行**：若一行只有 `[1]`，删角标后变空 → 删行并参与空行压缩，不留孤零空行。
- **署名行**：`^(编辑|责编|…|作者)[:：]` 仅删「标签: 值」整行；正文中出现「作者认为…」不带冒号结尾标签，不误删。
- **`collapse_blank_lines=false`**：保留原始空行结构（仅去首尾空行），用于需要严格保留排版的场景。
- **全部开关关闭**：`clean_article` 仍会去首尾空行，但不删噪声、不折叠——近似原文（消费层在未启用任何策略时直接返回原文，不进本函数）。

## 3. 与 LLM 润色（polish-ocr）的分工

| 维度 | 本技能（确定性清洗） | LLM 润色 |
| --- | --- | --- |
| 依赖 | 零模型，纯规则 | 需 LLM 出网 |
| 操作 | 只减不增、逐行 | 可改写、可概括、可重组 |
| 结果 | 可复现、可审计 | 不确定、需人工复核 |
| 适用 | 链接正文批量去噪 | 需要措辞润色/结构化时 |

同一入口 `POST /api/knowledge/polish-ocr` 按 `scope=polish` 策略做确定性清洗；需要改写/结构化时
才走 LLM 路径。二者互补，不互相替代。

## 4. 消费流程（polish-ocr）

```
text → skill_service.polish_policy(user)  # 合并已启用 polish 技能
  │  若四个布尔全关且无 extra_line_patterns → 直接返回原文（附「未启用清洗」提示）
  ▼
article_clean.clean_article(text, policy) → { cleaned, stats }
  ▼
组装 message：移除 N 处噪声行 / 删除 M 个角标 / 压缩 K 处多余空格
```

失败（异常）时返回原文并附错误信息，保证不丢用户数据。
