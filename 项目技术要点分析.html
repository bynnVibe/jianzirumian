关键架构决策

  • Agent 与 Proxy 分进程部署：同一镜像两种启动形态。Agent 持有 .agent-runtime.lock 文件锁（core/agent_runtime.py），保证单 Agent 单写者；Proxy 不取得锁、不恢复业务任务， 只做模型出网。启动时 recover() 把重启前处于 processing/parsing/running 的编译队列、上传、评测、流水线任务 复位为 pending/interrupted/aborted——崩溃恢复语义显式化，而非静默丢失。
  • 所有模型出网统一收口网关：业务代码不直接持有上游 Key，一律 LLMFactory.create_for_role(role, user_id, rule_id, model)，由网关按 15 个业务角色 （chat_answer / intent_rewrite / evidence_check / tool_decision / wiki_compile / embed / rerank / ocr / memory_extract / session_summary …） 解析路由规则与上游。这是「限额、审计、故障切换、语义缓存」能全局生效的前提。
  • 双源配置：.env 提供默认值，runtime_config.json（系统设置页）运行时覆盖； 检索模式、Wiki 开关、游客限额、压缩阈值等均可热调。
  • 同步重活隔离：embedding/rerank/OCR 等 CPU/网络重活放入线程池（交互默认池）与 heavy_executor 重活池（批量入库专用），避免批量上传拖慢交互请求；全链路用 call_context（ContextVar）把线程池内的调用归属回发起用户。
  • 请求级总预算：request_budget.iterate(deadline) 给每个 SSE 流套上 CHAT_REQUEST_TIMEOUT（默认 300s）硬预算，超时取消该会话全部生成任务并写告警、落 checkpoint。
没有「单写者锁 + 崩溃恢复」，多 worker 并发写 SQLite/FAISS 会产生索引撕裂与任务幽灵； 没有「网关收口」，每个模块各自持 Key 出网，限额/审计/故障切换都无从谈起——这正是许多 Demo 级 Agent 与生产系统的分水岭。

1.3 案例：系统从用户发出消息到完成任务，经历哪些步骤

以 ChatService.chat_stream（services/chat.py）为唯一主线，一次提问 = 一条 trace。 下面是全量步骤清单（含所有分支的触发条件），随后 1.4 节按场景抽取子集画数据流图。

01追踪与预算启动：obs.start_trace 开 trace；call_context 绑定发起用户；设置 300s 总预算 deadline；注册当前 asyncio 任务到会话活跃任务集（供「停止生成」取消）。
↓
02会话归属校验：get_session 按需从 SQLite 加载；user_id 不匹配直接拒绝（多租户隔离第一道闸）。若携带 resume_checkpoint_id，认领中断任务 checkpoint（pending→continued）。
↓
03用户消息落库：附件元数据随消息持久化；parse_command 解析 @skills / @tool 显式能力命令（命中则转「能力发现草稿流」，需登录且不与附件同轮）。
↓
04附件工具编排（有附件时）：tool_orchestrator 按文本意图 + 附件类型路由到 OCR / 入库 / 总结工具，统一经 invoke_tool 治理；图片 OCR 文本并入检索查询（截图检索），纯贴图提问以识别内容为问题。
↓
05上下文分区装配：静态系统提示（prompt_store 已发布版本 + FINAL_ANSWER_RULES 固定尾规）→ 五层记忆 Managed→User(L1 指令)→Project→Local 依次注入 → U 区常驻画像卡 → 启用 Skill 提示注入。每段 note_segment 记账。
↓
06语义缓存探针（资格门控：无附件/联网/命令/强刷/续任务、无逐轮个性化上下文）：先做意图改写，再携 profile_hash / skills_hash 向网关 probe；命中 → 分块回放缓存答案 + 来源，跳过检索与生成，直接收尾。
↓
07个人 Skill / 工具匹配：skill_runtime.prepare_for_query 按目录匹配并核验依赖资源（read_agent_skill 受控读取）；personal_tools / tool_workflow.select_for_query 选出本轮已授权工具集；依赖身份变化即报错不执行。
↓
08历史窗口构建：session_summary.build_context_messages —— 有摘要则「摘要 + continuation 指令 + 覆盖点之后 tail」，无摘要则冻结窗口；两档冻结 clip + 空闲衰减（三级压缩链的第一级在此生效）。
↓
09复杂度分流：classify_complexity 启发式预筛（≤30 字且无多步连接词→fast）+ LLM 细判（8s 超时保底 fast）。simple→fast 固定流水线；moderate→ReAct；complex→Plan&Execute。「沉淀 Skill」意图强制 ReAct。带附件/已选工具/续任务时跳过分流。
↓ 以下按模式分叉，见 1.4 场景图
10fast 路径：意图改写（query/scope/freshness，8s 超时回退原句）→ 场景路由 RouteDecision → 知识检索（线程池）与联网搜索并行 → Rerank + 相关度过滤 + Wiki 卡片前置 → Self-RAG 证据充分性判断 → 不足则拼接缺失要点重检一次 → 仍不足且意图模糊则 clarify 追问（HITL）→ KB 无命中未开联网则 need_search 询问（HITL）。
↓
11回答提示词构造：按路由主来源决定知识库/搜索结果权重（实时查询以联网为主依据，消除「知识库未收录」指令淹没搜索结果的答非所问）；双来源命中时强制「先知识库 [来源 X] 后联网 [网络来源 X] 再综合」结构。
↓
12缓存合同签发 + 流式生成：cache_policy.decide 判定可缓存性并 sign_contract（含证据充分性/依赖修订号/画像与技能哈希）经 extra_body 传给网关；LLMFactory.create_for_role("chat_answer") 延迟创建客户端；SSE token 逐块下发；网关侧可能命中语义缓存直接合成响应。
↓
13引用核对（Self-RAG 第二环）：verify_citations 检查 [来源 X] 编号越界，越界追加甄别提醒。
↓
14能力缺口闭环（回答生成之后）：answer_indicates_failure 启发式 + detect_scenario 判定「回答是否真正解决问题」；有低危工具配方 → auto_resolve 服务端自动执行并回喂；未解决 → capability_gap 卡片如实说明限制（DeepSeek 式降级）；同场景累计 ≥3 次提示沉淀为 Skill/工具。
↓
15收尾与后台巩固：助手消息 + 过程快照 v2（steps/intent/trace_id）落库 → 同一请求预算内依次执行：模块召回度量 flush、会话摘要 maybe_summarize（第二级压缩）、记忆抽取 extract_from_turn、记忆巩固 consolidate_if_due → 用量统计 → done 事件（单一 done 所有者 = chat.py）。
↓
16异常终态兜底：超时/取消时持久化「[生成已中断]」助手消息（刷新不丢上下文）、打包 checkpoint（继续/放弃）、写超时告警；obs.end_trace 记录 ok/error/timeout/cancelled 终态。

2 · Agent 大脑

「大脑」由五个子系统协同构成：提示词决定模型「是谁、按什么规矩说话」；意图识别决定「这句话要什么」； 上下文工程决定「模型这一刻能看到什么」；运行时决定「怎么一步步把事做完」；记忆决定「跨会话还记得什么」。 五者在一轮对话中的协作顺序如下：

入口意图改写 + 复杂度分流
→
装配上下文工程（画像/记忆/历史/证据分区）
→
执行运行时 Loop（fast / ReAct / Plan）
→
沉淀后台记忆抽取 + 会话摘要压缩

核心设计哲学：每个 LLM 决策点都有确定性保底（超时/解析失败 → 降级到保守路径）， 每个写入点都有门禁（查重/敏感词/容量/互斥），每个循环都有硬预算（步数/时长/重复签名）。 这是「大脑」不会失控的三道保险。

设计原理：提示词的组成结构

chat 主流程的系统提示词由 chat._build_system_prompt() 装配，结构为三段拼接：

# backend/app/services/chat.py + prompt_store.py + core/llm.py
system_prompt = prompt_store.get_active_body()   # ① 可治理正文（published 版本，无则回退 DEFAULT_BODY）
              + FINAL_ANSWER_RULES               # ② 固定尾规：只输出最终回答、Markdown 表格偏好等
# ③ 运行时注入（在 messages 层而非 system 层）：
#    U 区：用户画像卡（≤6 条 / 300 字）  D 区：相关记忆（评分 Top-K）
#    L1 指令：知识引用契约（[n] 编号、不得编造来源）  C 区：压缩后的会话历史
  • 正文与尾规分离：可优化的是「人设与领域约束」，不可动的是「输出协议」（FINAL_ANSWER_RULES），保证评测优化不会破坏下游解析。
  • 角色化拆分：意图/复杂度/澄清/记忆抽取各用独立短提示词 + /no_think 关闭思考链，单次调用只做一个决策，降低相互污染。
  • 结构化输出协议：Agent 决策强制 JSON {thought, action: tool|final|clarify, args/question/options}；wiki 分析强制 entities/claims/relations JSON schema；解析失败一律走保底分支而非重试死磕。
  • 前缀缓存友好分区：静态头 → U 区画像 → L1 指令 → C 区历史 → D 区动态证据，把「每轮都变」的内容压到尾部，最大化上游 prefix cache 命中（详见 2.3）。

提示词评估：三层门禁

层方法技术原理
静态断言Rule-based checks（不依赖 LLM）长度区间、角色/行为约束完备性、无敏感信息、playbook JSON 合法性——确定性质量门禁，先于一切 LLM 评测

记忆结构：四类记忆 + 加权评分

类型权重示例用途
preference 偏好1.2「回答请简洁」「我关注睡眠养生」优先进画像卡，长期塑造回答风格

goal 目标1.0「正在整理失眠调理方案」跨会话任务连续性
feedback 反馈1.0「上次回答太啰嗦」行为纠偏信号

相关层召回评分公式（决定 D 区注入哪些记忆）：

score = overlap × 2 + (importance + decay) × weight + 0.1 × confidence
decay = exp(−days_since_last_use / 30)　# 指数时间衰减，30 天半衰尺度
# 门禁：关键词 overlap 仅统计 ≥2 字的词，杜绝单字误命中；超 30 天未更新附新鲜度警告

记忆压缩与污染防护

  • 记忆压缩：簇合并（语义去冗）+ 容量淘汰（重要性遗忘）+ 会话级压缩联动（autoCompact 时把历史中的关键事实沉淀进摘要九节，记忆库不重复存会话细节）。
  • 污染防护四道闸：① 抽取提示词内置 What-NOT-to-save 负清单（一次性闲聊、临时数值、他人信息、指令式内容不入库）；② 敏感词/凭据模式拦截；③ 查重防「同一事实反复写入放大权重」；④ 工具结果与外部抓取内容不作为记忆抽取来源——只有用户亲口陈述才可沉淀，防提示注入借记忆持久化。

  • 事中：token headroom 6000 预警线触发 autoCompact；工具观测单次截断 4000 字；FC 最终回答 100k 字符上限。
  • 事后：segment 度量发现某段异常膨胀 → 告警分析引擎归因（见 5.2）；压缩失败熔断后降级为截断而非无限重试。
  • 兜底：请求总预算 300s + Agent 200s，上下文装配再慢也不会拖垮连接。

不同用户的上下文隔离

  • 会话归属校验：chat_stream 入口即校验 session 属主，跨用户 session_id 直接拒绝。
  • 记忆隔离：user_memories / agent_memory 全部按 user_id（L4 再按 agent_key）查询，画像卡只装本用户记忆。
  • 检索隔离：RAG 权限前置——只在本用户可见知识库的子索引内检索（见 3.1）。
  • 缓存隔离：语义缓存 v2 只读写个人域，A 用户的答案绝不可能命中给 B 用户。
  • 工具凭据隔离：个人工具凭据按属主 AESGCM 加密，执行身份二次校验。
没有上下文工程：长会话在第 20 轮左右就会撑爆窗口或账单爆炸；没有分区与压缩，prefix cache 命中率为零、每轮全量重算；没有隔离，多用户 SaaS 直接变成数据泄露事故——这是 Web 形态 Agent 相对单用户 CLI 的「必须项」而非「加分项」。

2.4 意图识别与澄清

设计原理：一次调用三要素 + 两级分流 + 证据驱动澄清

意图层回答三个问题：用户到底要查什么（query 改写）、这事有多难（复杂度分流）、信息够不够动手（澄清判定）。 设计上刻意把三者拆成独立小决策，每个都有 8s 超时与保守保底——意图层宁可「少聪明」，不可「挡主路」。

运转流程

① 意图改写intent_rewriter.analyze_intent：一次 LLM 调用（/no_think）产出三要素 JSON——query（≤20 字检索友好改写）、scope（public 公共知识 / personal 个人笔记）、freshness（static 静态 / dynamic 实时 / unknown）。失败回退：原句 + personal + 实时词兜底（「今天/最新」等词启发式判 dynamic）
↓
② 复杂度分流query_complexity：先启发式——≤30 字且无多步连接词（「然后/接着/对比/分别」等）直接判 fast，零 LLM 成本；否则 LLM 细判 simple/moderate/complex（8s 超时保底 fast）。映射：simple→fast 单轮直答、moderate→react 工具循环、complex→plan_execute 规划执行
↓
③ 任务分类freshness=dynamic → 触发 web_search 并行；scope=personal → 个人库优先；命中个人工具场景（天气/汇率等）→ router.RouteDecision 确定性直调；含「沉淀 skill」类诉求 → skill_distill 工具链
↓
④ 意图澄清intent_clarifier（evidence_check 角色，8s 超时保底不澄清）：仅当证据缺口源于意图本身模糊时才发 clarify 卡片（question + options 选项）；证据不足但意图明确 → 走重检/need_search 而非追问用户

任务规划与分解（Plan&Execute）

  • complex 任务先由 LLM 产出计划（≤MAX_PLAN_STEPS=5 步），前端以 plan SSE 事件渲染步骤清单，逐步执行并回报进度。
  • v1 采用静态计划（不动态重规划）：每步内部仍是 ReAct 小循环，步间失败走降级回答而非推倒重来——用「计划稳定性」换「可预测的成本与时长」。
  • 规划提示词约束每步必须可由现有工具（search_knowledge / web_search / find_skill_material / save_personal_skill）完成，杜绝「画饼式计划」。

RAG 更新、可观测性与评估

  • 更新机制：两段式上传（先传文件入库登记，再异步解析索引）；sha256 指纹去重防重复入库；素材更新触发增量重索引；Wiki 侧 source_hash 增量编译（见 3.2）；删除素材同步清理向量/倒排条目。

  • 与 LLM-Wiki 协同：Wiki 卡片作为 is_wiki_page 特殊 chunk 回写向量库，检索时稳定前置——「先给体系化结论，再给原始碎片佐证」；Wiki 知识助手反过来用 RAG 检索作为 read 工具的证据源。
没有 RAG：模型只能靠参数化知识回答健康养生问题——幻觉率不可控、无法引用用户自己的笔记、知识更新必须重训模型；没有混合检索与重排：专有名词漏召回 + 语义噪声多，引用质量崩塌；没有权限前置：多用户知识库互串，直接是数据安全事故。

3.2 LLM-Wiki 知识编译

设计原理：把「碎片笔记」编译成「体系化百科」

RAG 的固有局限：检索返回的是碎片，用户问「失眠怎么调理」得到 5 段互不关联的笔记摘录。 LLM-Wiki 的思路是离线知识编译——用 LLM 把散落素材预编译成结构化词条（概念卡）， 运行时直接命中「体系化结论」，碎片退居佐证。这相当于给知识库加了一层「编译器」： 素材是源码，Wiki 是产物，source_hash 是增量编译的依据。

4.1 Function Calling

工具的定义

  • 内置工具：search_knowledge（RAG 检索）、web_search（联网）、find_skill_material / save_personal_skill（技能沉淀）等，以 OpenAI 兼容 JSON Schema 声明（name/description/parameters），schema 总大小上限 65536 防撑爆请求。
  • 个人工具：用户自定义 HTTP API 工具，走 personal_tool_specs 声明式规范（endpoint/method/参数 schema/结果契约），版本不可变、确认幂等、属主隔离；凭据 AESGCM 加密独立存储。
  • 注册门禁：聊天目录 catalog、标准化注册表、Skill 依赖可用性三处一致要求 eval_status='passed'——评测不通过的工具不可被聊天调用，只在治理中心暴露阻塞原因。

工具调用流程（native.run_tool_loop）

1装配工具 schema + tool_choice=auto 发起 LLM 调用（经网关，角色绑定模型）
↓ 模型返回 tool_calls
2invoke_tool 统一入口：未知工具拒绝 → 个人工具 resolve（属主/版本/凭据）→ 五闸钩子（见下）→ 执行 → 异常一律转结构化 ToolResult（不抛裸异常进循环）→ record_tool_routing 落观测（含 schema_tokens；个人工具 args 只记 input_hash 防凭据入日志）
↓
3结果以 tool 消息回填，继续循环；max_calls≤6、总时长 90s；最后一轮强制 tool_choice=none 逼模型收敛出最终回答（final 上限 100k 字符）
↓

调用链分析与报错解决

  • 调用链分析：每次调用落 tool_routing 记录（工具名/路由决策/schema_tokens/耗时/三态结果），trace 页可展开完整 span 链；网关日志同时记录上游视角的工具调用，双视角对账。
  • 报错分级处理：① 参数错（validation）→ 回执带 schema 错误详情，模型下轮自纠；② 执行错（execution）→ 同 (tool,args) 签名失败 ≥2 次阻止重试并提示换路；③ 协议错（ToolProtocolError/ToolModelUnavailable）→ 降级为无工具直答；④ 重复 call_id → 直接拒绝防回放；⑤ 能力缺口 → capability_gap 流程（recipe 地理编码→open-meteo/wttr.in 补齐、auto_resolve LLM 判定可解性、不可解出 limitation 降级卡、同场景 ≥3 次提示沉淀为工具）。
  • 确定性直调旁路：router.RouteDecision 对天气/健康域等明确场景直接走 direct.py 确定性调用（需求契约 + WMO 天气码翻译），不消耗模型决策——复杂意图才回退 FC。
没有 FC 治理层：模型幻觉参数直接打到真实 API（凭据泄露/费用失控）；失败无三态区分，模型把报错当事实继续编造；无评测门禁，坏工具上架即污染所有用户的回答。

↓ stdin 注入 {code, data}
容器内runner.py：仅随固定镜像运行（Python 3.11 stdlib，无第三方依赖）；exec 已审批代码 → 调 main(data) → 结果契约校验后返回；禁止在业务后端或 Worker 主进程导入执行用户代码
核心不变量：隔离环境不可用 → 返回 sandbox_unavailable，绝不退回主机子进程。取消语义同样严格：控制连接不可用时抛 CancellationUnconfirmed，不能把「取消请求已发」宣称为「容器已终止」。
没有 CLI 治理：模型拼出的 shell 命令就是 RCE 漏洞（rm -rf / 反弹 shell / 凭据外传）；没有沙箱分层：动态代码与业务后端同进程，一次恶意工具即可拖库；没有「失败关闭」：沙箱挂了自动降级回主机，等于沙箱形同虚设。

短板：单机 Compose 拓扑无高可用（对比 Codex 云端托管）；SQLite/FAISS 决定垂直扩展上限；自建监控栈本身需要维护，小团队可先只跑业务告警轨。

6.2 定位差异：不是谁更强，而是解不同的题

Claude Code / Codex：单用户编码 Agent。信任模型是「用户坐在终端前/PR 审查兜底」，所以敢给模型极大执行自由；质量裁判是「测试跑通」这一确定性信号。上下文压缩与记忆层级是它们的原创范式，本系统直接对齐。

OpenClaw：单用户开放域个人助理。强在多渠道接入与 Skills 生态活力；弱在治理（配额/审计/评估缺失），单用户形态使其可以接受这些缺失。

见字如面：多用户垂直域知识 SaaS。没有「用户按 Esc」与「测试跑通」两大兜底，因此把安全、配额、评估、可观测全部制度化——用工程确定性替代人在环的即时判断。RAG + LLM-Wiki 是其相对所有对比对象的独有能力层。

可借鉴方向：① 引入 MCP 兼容层补齐工具生态广度；② subagent 并行委托提升复杂任务上限；③ 动态重规划替代静态计划；④ 沙箱镜像分层扩展（数据分析/绘图依赖包）；⑤ 存储层向 Postgres + 托管向量演进以突破单机上限。

6.3 一句话总结

「见字如面」证明了一件事：生产级 Agent 的竞争力不在模型，而在模型周围的制度—— 提示词有版本与评测、记忆有门禁与遗忘、上下文有预算与压缩、循环有步数与熔断、工具有闸门与门禁、 出网有网关与审计、发布有回归与灰度。这套「制度总和」，正是它与 demo 级 Agent 的分界线， 也是本仓库作为 Agent 系统工程样本的最大价值。
