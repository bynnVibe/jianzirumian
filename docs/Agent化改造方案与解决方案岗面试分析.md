# 第一部分：往 Agent 方向靠，改什么

## 0. 先做一个关键判断：不是所有地方都该 Agent 化

这是改造前必须想清楚的，也是面试时最能体现判断力的一点。

| 模块 | 建议 | 理由 |
|---|---|---|
| **RAG 主链路**（检索 → 重排 → 生成） | **保持确定性流水线，不 Agent 化** | 延迟敏感（用户等流式输出）、执行路径确定。交给模型"自主决定检索几次"会引入不可控延迟与波动，收益覆盖不了成本 |
| **意图理解与工具选择** | **Agent 化，收益最大** | 关键词路由处理不了复合指令和参数抽取 |
| **多步任务**（跨库整理、批量入库、生成报告） | **Agent 化，这是真正的增量** | 当前系统完全没有多步执行能力 |
| **证据评估与重检** | **从单次改为有界循环** | 现成的基础已有，改造成循环成本很低 |

**结论**：Agent 化应该落在**"理解意图 + 选工具 + 多步编排"**上，而不是把已经很稳的检索链路打碎重来。这个取舍本身就是判断力的体现——无脑全盘 ReAct 化是新手做法。

## 1. Phase 1：工具层 Function Calling 化（1~2 周，性价比最高）

### 现状问题

`tool_orchestrator.py` 里的路由是关键词硬匹配：

```python
_UPLOAD_KEYWORDS = ("上传", "保存", "入库", "加入知识库", ...)
def _decide_action(query: str) -> str:
    if any(k in query for k in _UPLOAD_KEYWORDS):
        return "upload"
```

它处理不了这两类真实需求：

- **复合指令**：「把这张图里的方剂整理一下，存进我的中医库」——既有 summarize 又有 upload
- **参数抽取**：「我的中医库」需要解析成具体的 `kb_id`，关键词完全无能为力

### 改造落点（三个文件）

**① `services/tools/base.py` — 给工具加参数 Schema**

现在 `BaseTool` 只有 `name` 和 `description`，模型无从知道参数。补一个 `to_schema()`：

```python
class BaseTool:
    name: str = "base_tool"
    description: str = ""
    parameters: dict = {"type": "object", "properties": {}, "required": []}

    def to_schema(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.parameters,
            },
        }
```

**② `core/llm.py` — 让 chat 支持 tools**

现在 `BaseLLM.chat(messages, stream)` 没有 tools 入参，这是根本阻塞点。改造后：

```python
async def chat(self, messages, stream=False, tools=None, tool_choice="auto"):
    ...
    response = await client.chat.completions.create(
        model=self.model, messages=messages, stream=stream,
        tools=tools, tool_choice=tool_choice,
    )
```

需要处理的兼容点：
- **Ollama** 新版 `/api/chat` 已支持 `tools` 字段，但部分小模型不支持 → 用配置开关 `LLM_SUPPORTS_TOOLS` 降级回关键词路由
- **DeepSeek / 通义** 兼容 OpenAI 格式，可直接传
- **流式 + tool_calls** 同时出现时的解析（delta.tool_calls 是增量拼接，不能按 content 处理）

**③ `services/tool_orchestrator.py` — 双路决策**

不要一刀切换掉关键词，**保留它作为兜底和护栏**：

```python
async def _decide_action(query, llm, tools, user_id):
    if not settings.LLM_SUPPORTS_TOOLS:
        return _decide_by_keywords(query)          # 降级路径
    try:
        decision = await asyncio.wait_for(
            llm_plan(query, tools), timeout=10
        )
    except asyncio.TimeoutError:
        return _decide_by_keywords(query)          # 超时兜底
    return _guard(decision, user_id)               # 权限护栏
```

**护栏（必做，面试高频考点）**：
- 危险工具（写知识库、删除）必须二次确认，走 SSE 发 `confirm_required` 事件，前端弹窗
- 游客身份禁止写操作（现有逻辑已有，保留）
- 工具白名单校验，模型返回未注册的工具名直接拒绝

### 这一阶段的收益（可直接量化）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 支持指令类型 | 单一意图 | 复合意图、带参数指令 |
| 工具选择准确率 | 无法评测 | 可建评测集量化 |
| 参数解析 | 不支持 | 支持 kb_id、日期范围等 |

## 2. Phase 2：编排层状态图化（2~3 周）

### 现状问题

`chat_service.chat_stream()` 是一段约 300 行的线性 `async` 函数，顺序固定：改写 → 检索 → 重排 → 证据判断 → 生成。想加"重试""分支""循环"只能继续堆 if-else，很快失控。

### 改造方案：引入 LangGraph 状态图

```
                    ┌─────────────┐
                    │    plan     │  理解意图、决定动用哪些能力
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
          ┌────────▶│  retrieve   │  混合检索（复用现有 _hybrid_search）
          │         └──────┬──────┘
          │                ▼
          │         ┌─────────────┐
          │         │  evaluate   │  证据充分性判断（复用 evidence_checker）
          │         └──────┬──────┘
          │          充分 ─┴─ 不足（且 iter < 3）
          │                ▼              │
          │         ┌─────────────┐       │
          └─────────│  generate   │◀──────┘
                    └─────────────┘
```

**关键设计**：

1. **有界循环**：`max_iterations = 3`，且重检前对已尝试过的查询去重，防止原地打转
2. **终止条件**：轮次上限 / 证据充分 / 超时预算耗尽（如 20s 强制进生成）
3. **状态持久化**：用 LangGraph checkpoint，支持中断恢复与审计回放
4. **前端零改动**：每个节点发出现有的 SSE `status.phase` 事件，`ChatView.vue` 的步骤条逻辑不用动

**这一步的真正价值**：现在证据不足只能重检一次，改成循环后可以「换检索策略」（比如从混合检索切到联网搜索、换知识库、换查询粒度），而不只是换查询词。

## 3. Phase 3：能力扩展与协议标准化（3~4 周）

### 3.1 MCP 协议化

把现有 4 个工具 + 新增工具封装为 MCP Server。2026 年这是工具互通的事实标准，面试高频词。

收益不只是"跟上潮流"——MCP 化之后，这套能力可以被 Cursor、Claude Desktop、其他 Agent 直接调用，从"一个问答系统"变成"一个可被编排的知识服务"。这在解决方案语境下是重要的卖点。

### 3.2 新增工具集（让 Agent 真的有活干）

现有 4 个工具（image_ocr / image_upload / document_import / knowledge_summarize）全部围绕"处理附件"，Agent 能做的事太少。建议补：

| 新工具 | 能力 | 支撑的场景 |
|---|---|---|
| `search_knowledge` | 语义检索知识库 | 多步任务中主动查资料 |
| `list_knowledge_bases` | 列出可见库 | 让模型自己解析"我的中医库" |
| `query_ingest_history` | 查入库历史 | "最近一个月入库了哪些" |
| `generate_wiki_digest` | 生成综合词条 | "整理成一份资料" |
| `compare_documents` | 多文档比对 | "这两份笔记有什么矛盾" |
| `export_report` | 导出 Markdown/PDF | 产出交付物 |

**注意**：工具不是越多越好。超过 10 个会显著降低选择准确率，需要做**工具语义检索**（按任务描述向量召回 Top-5 再交给模型选）。这一点主动讲出来很加分。

## 4. 强烈建议做的一个业务级 Agent：知识入库 Agent

这是我认为**投入产出比最高**的一个改造，因为它有明确业务价值，且能复用现有全部能力。

**现状**：用户上传一批手写图 → 人工逐张看效果 → 手动选知识库 → 逐条入库。步骤繁琐。

**Agent 化后**：用户丢一批图 + 一句「整理进我的养生库」，自动完成：

```
1. 批量 OCR 识别
2. 质量评估（模糊检测已有前端实现，移到后端 + 置信度判断）
   └ 低质量 → 标记并请求人工确认，不静默入库
3. 内容分类 → 判断归属知识库（调 list_knowledge_bases + LLM 判断）
4. 去重 → 与已有知识向量比对，重复的不入库
5. wiki 编译（现有能力）
6. 汇报：入库 N 条，跳过 M 条及原因
```

**为什么这个场景值得做**：
- 真正的多步任务，体现 Agent 价值
- 有明确的"人工介入点"（低质量图片确认），符合 HITL 最佳实践
- 可评测：入库准确率、去重准确率、分类准确率，能量化
- 复用现有 OCR / wiki / 向量库能力，改造量不大

---

## 5. 明确不该做的：Multi-Agent

**不建议**为这个场景上 Multi-Agent。理由：

- 任务主体是"检索 + 生成"，单 Agent 足够
- 多 Agent 带来协调成本、延迟翻倍、调试复杂度激增，收益不明确
- 业界共识：**先证明单 Agent 的局限，再考虑多 Agent**

**什么时候才需要**（面试可以这么答）：当出现明确的角色分工且子任务可并行时——比如"研究型问答"场景，一个 Agent 负责检索、一个负责校验、一个负责写作，此时并行收益才覆盖协调成本。

主动说明"什么不该做"，比罗列一堆技术栈更能体现方案能力。

---

## 6. 改造优先级建议

| 顺序 | 事项 | 周期 | 面试价值 |
|---|---|---|---|
| 1 | Function Calling + 工具 Schema | 1~2 周 | ★★★★★ 补齐最关键短板 |
| 2 | LangGraph 状态图 + 有界循环 | 2~3 周 | ★★★★★ 从流水线变成 Agent |
| 3 | 知识入库 Agent（业务场景） | 2 周 | ★★★★☆ 有业务价值的完整案例 |
| 4 | MCP 化 + 新增工具集 | 2 周 | ★★★★☆ 协议标准化 |
| 5 | Langfuse 可观测 + 记忆分层 | 1~2 周 | ★★★☆☆ 生产化补全 |

做完 1 + 2，就可以比较踏实地投 Agent 开发岗了。

# 第二部分：面试 AI 解决方案 / 大模型解决方案岗

## 1. 先搞清楚这个岗位到底要什么

解决方案岗 ≠ 开发岗。它考察的是：

| 维度 | 具体 |
|---|---|
| 需求拆解 | 把模糊业务诉求转成可技术方案 |
| 方案设计 | 技术选型 + 架构设计 + **选型理由** |
| 落地能力 | POC → 上线 → 运维，能不能真跑起来 |
| 成本意识 | TCO、token 成本、硬件成本、ROI |
| 风险合规 | 数据安全、私有化、权限隔离、幻觉治理 |
| 交付沟通 | 方案宣讲、客户对齐、预期管理 |

**关键差异**：开发岗深挖代码，解决方案岗深挖**"为什么这么选、换场景怎么调、客户会问什么"**。

---

## 2. 优势

### ★★★★★ 优势一：多 Provider 可切换架构 —— 这是解决方案岗的核心卖点

项目对 LLM / OCR / Embedding / Rerank / Search **五类能力全部做了工厂模式抽象**，且支持**运行时热切换**（系统设置页改配置即生效，无需重启）。

这直接命中解决方案岗最核心的命题：**客户环境各异，方案必须能适配**。

面试时可以这么讲：
> 有的客户要求私有化、有的已经采购了阿里云、有的只想用开源模型省钱。我把五类外部依赖都做了抽象，同一套代码可以跑在全本地（Ollama + PaddleOCR + FAISS）也可以跑在纯云端，客户换了供应商不用改代码，在系统设置页切换就行。

这是**最能打动解决方案面试官**的一点，务必重点准备。

### ★★★★★ 优势二：端到端交付完整度

从 OCR → 解析 → 入库 → 检索 → 问答 → 引用溯源 → 收藏 → 部署 → 备份 → HTTPS，**全链路跑通且能上线**。

大量候选人只有"调 API 跑通 Demo"的经验，而这个项目有 Docker Compose、阿里云部署脚本、定时备份、镜像瘦身。这证明你懂"交付"不只是"跑通"。

### ★★★★☆ 优势三：成本优化的实证

解决方案岗核心就是 TCO。项目里有多个可量化证据：

- 后端镜像瘦身 **2.27GB → 574MB（-75%）**
- OpenRouter 免费模型自动降级切换，模型不可用时自动换一个重试
- 本地 / 云端双方案，低配服务器也能跑
- Redis 缓存 + 60s 冷却降级，不可用时功能不受影响
- 全链路超时保护（意图改写 15s、证据判断 15s），避免无效 token 消耗

### ★★★★☆ 优势四：权限与数据安全设计

ToB 客户必问。项目里有：

- 向量库**物理隔离**（`_scoped_store` 重建子索引），不是检索后过滤
- 游客限流 + IP 哈希脱敏
- 记忆抽取的敏感信息正则拦截（密码/身份证/银行卡不落库）
- 私人知识库仅属主可见，管理员也不越权

### ★★★★☆ 优势五：回归评测体系

POC 阶段客户最常问："你怎么证明效果好？改了之后怎么保证不退步？"

项目有完整的答案：检索命中率 + 引用忠实度 + LLM-as-Judge，支持跨 run 对比，还能把用户点踩的真实问题自动转成评测用例。这个闭环在 POC 汇报时非常有说服力。

### ★★★☆☆ 优势六：垂直场景的真实理解

手写笔记这个场景有真实业务链条：**OCR 质量 → 入库 → 检索 → 引用溯源**。项目对每一环都有针对性处理（模糊检测、表格转 Markdown、按页溯源、引用编号核对）。说明你能深入业务细节，不是套通用模板。

### ★★★☆☆ 优势七：文档与交付物质量

README 1446 行，含部署检查清单、FAQ、备份方案、HTTPS 配置、故障排查。解决方案岗很看重能不能产出高质量交付文档。

## 3. 劣势

### 🔴 劣势一：单场景、单行业，缺跨行业推演能力

只有健康养生笔记一个场景。解决方案岗要求"能给不同客户出方案"，你需要能现场推演："如果客户是律所/医院/制造企业，这套方案怎么调？"

**这是最大的短板，必须提前准备 2~3 个行业推演。**

### 🔴 劣势二：没有量化业务价值

项目里没有 ROI 数据：效率提升多少？人工节省多少？用户满意度？

解决方案岗靠数据说话，说不出"帮客户省了多少钱"会明显吃亏。

**补救**：即使没有真实数据，也要准备一套**测算方法**（比如：人工整理一份笔记 X 分钟，系统 Y 分钟，准确率 Z%，按 N 人规模年节省多少工时）。

### 🔴 劣势三：无规模与并发数据

客户必问"支持多少人同时用？知识库能放多大？检索延迟多少？"——当前答不上来。

**补救（面试前必做）**：补一组压测数据，做成一页纸：
- 知识库规模（1k / 10k / 100k chunk）× 检索 P50/P99 延迟
- 并发用户数 × 响应时间
- 硬件配置与成本对照

### 🟡 劣势四：缺选型论证的沉淀

README 有"关键设计决策"表，但太薄（只有一句理由）。解决方案岗要的是**对比论证**：

- 为什么选 FAISS 不选 Milvus / pgvector / Weaviate？什么规模下必须迁？
- 为什么选 SSE 不选 WebSocket？
- 为什么 SQLite 够用，什么时候必须换 PostgreSQL？

**补救**：把选型写成一页对比表，含"什么条件下这个选型会失效"——这才是方案能力的体现。

### 🟡 劣势五：无私有化 / 信创方案

当前部署方案绑定阿里云。政企客户必问私有化、国产化、离线部署。

**补救**：项目其实**技术上完全支持全离线**（Ollama + PaddleOCR + FAISS + SQLite），只是文档没强调。面试时把"全本地零外网方案"作为独立方案讲出来，这是现成的牌。

### 🟡 劣势六：无多租户 / 计费 / 配额体系

有游客限流和用户用量统计，但不是租户级隔离与配额。SaaS 化方案能力缺失。

### 🟡 劣势七：方案形态单一

只做过 RAG。没做过微调、多模态、工作流编排、Agent 等其他形态。解决方案岗需要知道"什么问题该用什么方案形态"，包括**什么时候不该用 RAG**。

---

## 4. 面试前必补的 5 件事

| # | 事项 | 说明 |
|---|---|---|
| 1 | **技术选型对比表** | 每类组件 3 个候选 + 选型理由 + **失效条件**。这是方案岗的核心交付物 |
| 2 | **一页纸 POC 指标卡** | 准确率 / 召回率 / 延迟 / 单次成本，做成可给客户看的一页纸 |
| 3 | **规模测算表** | 知识库规模 × 延迟 × 硬件 × 成本，三档配置对照 |
| 4 | **3 个行业推演** | 律所（合同问答）、医院（病历/指南）、制造（设备手册），各写一份方案调整要点 |
| 5 | **全本地私有化方案** | 把现有 Ollama + PaddleOCR + FAISS 组合包装成独立交付方案 |

## 5. 话术示例

### 5.1 怎么介绍这个项目（解决方案岗版本，注意和开发岗版本不同）

> 这是一个面向个人知识管理的问答系统，核心价值是把手写笔记这种**非结构化、难以检索**的内容变成可问答的知识资产。
>
> 方案上我做了几个关键设计：
>
> 第一是**供应商解耦**。LLM、OCR、向量化、重排、搜索五类能力全部抽象成接口，可以全本地部署也可以全云端，客户换供应商不用改代码。这对交付很重要，因为不同客户的环境差异非常大。
>
> 第二是**检索质量**。用了稠密加稀疏的混合召回再做重排，还有一层知识编译——把原始碎片预先整理成百科词条，检索时优先命中，比直接捞碎片效果好。
>
> 第三是**可验证**。我建了一套回归评测，每次改策略都能跑一遍看有没有退步，用户点踩的问题会自动进评测集。POC 阶段能给客户看到量化指标，而不是"感觉还行"。
>
> 成本上也做了优化，比如后端镜像从 2.3G 瘦到 574M，模型限流时自动切换，低配服务器也能跑。

### 5.2 被问"这个方案换个行业能用吗"（必考题）

> 底层能力是通用的：文档解析、向量检索、引用溯源这三块跟行业无关。真正要调的是三处：
>
> 一是**文档解析**——行业文档格式差异大，法律合同有条款结构、病历有表单、设备手册有大量图表，解析器要针对性适配，我做表格转 Markdown 就是这类工作。
>
> 二是**术语与分词**——通用 embedding 在专业术语上效果会掉，我的自研 BM25 分词策略也要按行业调，必要时换领域 embedding 或做术语表增强。
>
> 三是**权限模型**——律所的项目隔离、医院的患者隐私等级，比现在的公共/个人两级复杂得多，需要引入角色和密级。
>
> 检索和生成的主体链路不用动，这也是我做供应商解耦和分层的原因。

### 5.3 被问"客户说效果不好，你怎么排查"（区分度的题）

给出一个结构化排查路径，这是方案岗最看重的：

```
1. 先定位是"检索没召回"还是"召回了但答错了"
   → 看评测集的检索命中率：命中率低是检索问题，命中率高但 judge 分低是生成问题
2. 检索问题往下拆：
   → 原文里到底有没有？（没有 → 知识库覆盖问题，不是系统问题）
   → 有但没召回 → chunk 切分 / embedding / 阈值三个方向
   → 召回了但排后面 → rerank 问题
3. 生成问题往下拆：
   → 引用忠实度低 → 模型没按证据答，调 prompt 或换模型
   → 忠实度够但 judge 分低 → 参考答案本身有问题，或评判标准没对齐
4. 每一步都有评测指标兜着，改完跑回归看有没有回退
```

这套"用指标定位，而不是拍脑袋"的思路，是区别于 Demo 选手的关键。

---

## 6. 总结

**Agent 化改造**：优先做 Function Calling（1~2 周）+ LangGraph 状态图（2~3 周），这两步做完就有底气投 Agent 岗。再补一个"知识入库 Agent"作为完整业务案例。RAG 主链路保持确定性，不要为了 Agent 而 Agent。

**解决方案岗**：最大王牌是**多 Provider 可切换架构**和**端到端交付完整度**，这两点直接命中岗位核心诉求。最大短板是**单场景**和**无量化业务价值**——提前补选型对比表、POC 指标卡、规模测算表和 3 个行业推演，基本能补齐。
