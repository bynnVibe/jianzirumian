## 见字如面项目整体技术分析 + AI 岗位面试匹配分析（只读分析，未改代码）

产出：`docs/项目分析与AI岗位面试匹配报告.md`

### 核心结论
- 项目真实定位：**生产级 RAG + 文档智能应用**，不是 Agent 系统。Agent 成分仅"关键词路由的单点工具调用"。
- 规模：后端 12,489 行 Python（30 模块）/ 前端 19,365 行 Vue3 / SQLite 20 表 / 测试仅 27 用例 / 无 CI / 4 次 commit。
- 强项：混合检索（FAISS + 自研 BM25 + RRF + Rerank + 知识库路由 >3 库时 broad search 选 Top3）、llm-wiki 知识编译层、向量库物理权限隔离（`_scoped_store`）、回归评测（LLM-as-Judge + 检索命中率 + 引用忠实度 + 点踩反馈转用例）、全链路降级与超时保护、Docker/阿里云部署。
- 短板：无 ReAct 循环、无规划、无 Multi-Agent、无 MCP/A2A、无可观测（Langfuse 级）、`_scoped_store` 每次检索 O(N) 重建子索引、SQLite 写锁 + FAISS 全量 save、prompt 未版本化、无压测数据。

### 岗位匹配结论
- 主投：大模型应用开发工程师、RAG 工程师、AI 全栈、Python 后端（AI 方向）、文档智能/OCR 应用。
- 慎投：AI Agent 开发（需先补 Function Calling + MCP + LangGraph 状态图）。
- 不投：大模型算法训练、AI Infra。

### 面试策略要点
主动交底"这不算严格 Agent，是 RAG 流水线 + 单点工具调用"，并给出演进路线（Function Calling + MCP + LangGraph），远好于硬撑。

## 追加：Agent 化改造方案 + AI 解决方案岗面试分析（只读，未改代码）

产出：`docs/Agent化改造方案与解决方案岗面试分析.md`

### 关键代码落点（为后续改造确认）
- `app/core/llm.py`：`BaseLLM.chat(messages, stream)` **无 tools 参数** —— Agent 化的根本阻塞点，需加 tools/tool_choice。
- `app/services/tools/base.py`：`BaseTool` 只有 name/description，**无参数 JSON Schema** —— 需补 `to_schema()`。
- `app/services/tool_orchestrator.py`：`_decide_action()` 关键词硬匹配 —— 改 LLM 决策 + 关键词兜底 + 权限护栏。
- 已有 4 个工具：image_ocr / image_upload / document_import / knowledge_summarize（全部围绕附件处理）。

### Agent 化核心判断（重要）
RAG 主链路**不要** Agent 化（延迟敏感、路径确定）；Agent 化应落在"意图理解 + 工具选择 + 多步编排"。主动说明"什么不该做"比堆技术栈更体现判断力。
改造路线：P1 Function Calling（1-2周）→ P2 LangGraph 状态图 + 有界循环 max 3 轮（2-3周）→ P3 MCP + 新工具集 → 可观测/记忆。
高价值业务场景：**知识入库 Agent**（批量 OCR → 质量评估 → 分类 → 去重 → wiki 编译 → 汇报），复用现有全部能力。
明确不建议上 Multi-Agent（协调成本 > 收益）。

### 解决方案岗结论
- 最大优势：① 五类 Provider（LLM/OCR/Embedding/Rerank/Search）工厂模式 + 运行时热切换 —— 直击"客户环境各异"核心命题；② 端到端交付完整度；③ 成本优化实证（镜像 2.27GB→574MB）；④ 权限物理隔离；⑤ 回归评测体系（POC 可量化）。
- 最大短板：① 单场景单行业缺跨行业推演；② 无量化业务价值/ROI；③ 无并发压测与规模数据；④ 选型论证太薄；⑤ 未把"全本地私有化方案"单独包装（其实技术已支持：Ollama+PaddleOCR+FAISS+SQLite）。
- 面试前必补：选型对比表（含失效条件）、一页 POC 指标卡、规模测算表、3 个行业推演（律所/医院/制造）、全本地私有化方案。
